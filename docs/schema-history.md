# Schema history

The migration chain that built this schema was squashed into a single baseline
(`apps/api/drizzle/0000_init.sql`) before the first deployment. This file is what the deleted
migrations *said* — the reasoning, not the DDL.

It is kept because roughly a third of those files was prose: why a column was added nullable and
backfilled rather than declared `NOT NULL`, which legacy status mapped onto which new one, why an
index's column order is what it is. The SQL is reproducible from the schema at any time; the
argument behind it is not.

**This file is history, not documentation of the current schema.** It describes decisions at the
moment they were made, and some have since been reversed — the daily-snapshot tables named below
were removed again, and the naive `timestamp` columns became `timestamptz`. For what is true now,
read the schema files and `apps/api/CLAUDE.md`. For how the squash was verified, see the
"Open Items" note on migrations in that file.

The original 19 files are recoverable from git history before the squash commit.

### `0006_wholesale_buy_domain`

Wholesale-buy domain rebuild: CREATED→CONFIRMED→PAID→RECEIVED→CHECKED plus the failure
branches, dual purity pricing, delivered-weight capture and the edit-window deadline.

Generated by drizzle-kit, then hardened by hand so it also applies to a populated table:
the legacy statuses are remapped while the column is text, and the two new NOT NULL columns
are added nullable, backfilled, then constrained.
legacy status remap, done while both columns are plain text:
  DRAFT   → CREATED  (old system status 1)
  SETTLED → CHECKED  (the old terminal state; inventory had already moved by then)
price_per_gb keeps its name and its meaning: the 96.5% quote. The 99.9% quote is derived from
it by the purity ratio for any pre-existing row; from here on the operator enters it.
delivered weight — null until the shipment is checked, and null when it matched the order
edit window deadline; pre-existing rows are past theirs by definition

### `0007_wholesale_sell_domain`

Wholesale-sell domain rebuild: CREATED→CONFIRMED→PACKED→SHIPPED→PAID plus the failure branches,
dual purity pricing, contested-weight capture and the confirm-sweep deadline. Mirrors the
wholesale-buy rebuild in 0006.

Hand-hardened the same way so it also applies to a populated table: the legacy statuses are
remapped while the column is plain text, and the new NOT NULL columns are added nullable,
backfilled, then constrained.
legacy status remap, done while both columns are plain text:
  DRAFT   → CREATED  the pre-confirmation state, now editable and swept by confirm-all
  SETTLED → PAID     the old terminal state — the money had landed by then
SHIPPED and CANCELLED keep their names. SHIPPED also keeps its meaning for inventory purposes:
the old model decremented on entering it, and in the new model anything at SHIPPED has already

PACKED entry in their status log, which is an accurate record of what the old system captured.
price_per_gb keeps its name and its meaning: the 96.5% quote. The 99.9% quote is derived from
it by the purity ratio for any pre-existing row; from here on the server derives it on write.
the weight the buyer contests — null until a shipped deal is disputed

### `0008_whole_buy_delivery_failed`

wholesale-buy gains the failure path its mirror already had: PAID → RECEIVED was previously
the only exit from PAID, so a supplier who took our money and never shipped stranded the
transaction there forever with no terminal.

  PAID            → RECEIVED | DELIVERY_FAILED
  DELIVERY_FAILED → RECEIVED | WRITTEN_OFF

This is the exact counterpart of the sell side's DELIVERED → PAYMENT_FAILED → WRITTEN_OFF:
in both domains it covers "the counterparty took the valuable thing and never handed over its
other half". Neither has a route to CANCELLED — ours already moved.

Pure additions to the enum, so ALTER TYPE ADD VALUE is used rather than the drop-and-recreate
dance in 0006/0007: no existing row changes value and no column has to round-trip through text.
Safe inside a transaction on PostgreSQL 12+ because the new labels are not read in this
migration. IF NOT EXISTS keeps it idempotent.

### `0009_wholesale_return_close_out`

Closes the one hole both wholesale domains still had: value that moved with nothing to show
for it and no way to record how it ended.

1. whole_buy CHECKED → STOCKED
   The status is renamed for what it does — it is the step that moves gold into inventory, and
   the old name described the clerical act instead. RENAME VALUE rewrites the label in place,
   so every existing transaction and status-log row follows it with no data migration.

2. whole_buy gains REFUNDED, and RETURNED stops being terminal
   RETURNED after PAID left the supplier holding our cash with the machine out of moves. It now
   resolves: REFUNDED (money back), RECEIVED (they re-delivered the correct item), or
   WRITTEN_OFF (they never made us whole).

3. settled_amount on both tables
   What was actually paid when it differed from total_amount. Null means it matched. Recorded
   on the move into PAID and never branched on — an accepted variance closes a deal exactly
   like an exact payment, so it is a figure accounting needs rather than a state anyone works.

4. return_reason on both tables
   Weight, brand or purity disagreeing with the document are three different failures, and
   supplier reliability is only reportable if the cause is a column rather than prose in a note.

ALTER TYPE ... ADD VALUE is safe inside a transaction on PostgreSQL 12+ because the new labels
are not read by any statement in this migration; RENAME VALUE has no such restriction. Both are
guarded so a re-run is a no-op.

### `0010_realign_drizzle_snapshot`

No-op. This migration exists only to repair drizzle-kit's snapshot chain.

Migrations 0007, 0008 and 0009 were hand-written: each added its SQL file and a _journal.json
entry, but none wrote a drizzle/meta/NNNN_snapshot.json. drizzle-kit does not read the database
when generating — it diffs the TypeScript schema against the *last snapshot*, which therefore
stayed frozen at 0006. `db:generate` consequently re-emitted every change since then as if it
were new: CREATE TYPE for types that exist, ADD COLUMN for columns that exist, and a
drop-and-recreate of both status enums. Running that output would have failed on the first
duplicate column, after having already cast two live enum columns to text.

The accompanying meta/0010_snapshot.json is the fix: it is a true snapshot of the schema as it
now stands, so future `db:generate` runs diff against reality. The database already has
everything in it, which is why there is nothing to execute here.

If you hand-write a migration again, write the snapshot too, or the next person gets this.

### `0012_business_transaction_date`

The business date every manually-created record now carries, alongside the insert timestamp it
already had. Rows written before this migration have only one date to offer, so their business
date is backfilled from their own insert timestamp — which is exactly what they meant when the
two could not be told apart.

Generated as a bare `ADD COLUMN ... NOT NULL`, which cannot apply to a table with rows in it.
Split into add-nullable → backfill → constrain. The resulting schema is identical, so the
drizzle snapshot generated alongside this file still describes it.

### `0013_product_switch_destination_brand`

a switch now names both ends. Every switch recorded before this landed in the fungible pool by
construction, so 'NA' is the true historical value, not a filler default — hence backfill then
drop the default, so nothing new can be written without saying where it went.

### `0016_inventory_movements_index`

The movement ledger had no index at all beyond its primary key on `id`, so every read of
`GET /inventory/movements` was a sequential scan plus an in-memory sort.

The column order matches `listMovements` exactly: the window bounds `movement_date`, and
`(moved_at, id)` breaks ties inside a day. One index therefore serves both the range scan and
the ordering, with no sort step left to do.

The reason to add it now rather than later is `sumMovementsBefore`, the opening-balance query.
It aggregates *everything* before the window's first day, so its cost tracks the age of the
ledger and not the size of the request — opening the page on yesterday–today gets slower every
month the shop trades. An Excel export invites wider windows on top of that.

Plain CREATE INDEX rather than CONCURRENTLY: the migrator runs each file inside a transaction,
which CONCURRENTLY forbids. The table is small enough today that the brief write lock is not
worth splitting this out into an out-of-band step.

### `0017_retail_manual_entry`

Retail becomes a manual write-up layer.

Both retail tables were built in 0000 as a *sync target* for a legacy POS, and were never used:
they hold zero rows. That POS integration is blocked on an unfinished document, and the shop
needs retail figures in the system now to compare buy against sell across all four transaction
domains. So the tables are reshaped for a human writing up a trade that already happened.

The sync-only columns are DROPPED rather than relaxed to nullable. A column whose only filler is
a service that does not exist reads as data someone forgot to populate, and re-adding it when the
sync service is built is a migration either way. Dropping is free here precisely because the
tables are empty — the same reason `transaction_date NOT NULL` needs no backfill.

Neither status enum is touched. `DRAFT` on both and `SHIPPED` on sell stay as values but become
unreachable through the shared transition map: a write-up lands directly on `CONFIRMED`, and the
inventory decrement that used to hang off `SHIPPED` is removed (retail moves no stock — stock is
adjusted manually via /inventory/gain|loss). Both come back by adding a transition, not a
migration. The `currentStatus` default moves to `CONFIRMED` to match.
The business day the deal happened, and the one the Fri–Thu settlement period is derived from.
Without it a backfilled week of trading would all land in the week it was typed up.
Fees sit BESIDE the total, never inside it: `total_amount` stays weight_gb * price_per_gb so it
is directly comparable against the wholesale domains, which carry no fees at all.
Marks how a row arrived, so a later POS feed is distinguishable from what was typed in by hand.
Brand keys an inventory pool, and retail no longer touches one. Left on the table for a future
coupling, but nothing may depend on it being present.
`branches` is the required counterparty-side FK on both retail tables and has never held a row,
so nothing could be inserted at all. It gains the instant the row was written and a tombstone.

`deleted_at` rather than a hard delete, because once transactions reference a branch, deleting it
is impossible. It is distinct from the existing `active`, which is the reversible "not trading
right now": a closed branch still has to resolve its name on every transaction it ever recorded.

There is deliberately no opening-date column. The shop's branch export carries one, but it is
empty for the thirteen oldest branches and nothing reads it — a column that is a third unknown
and answers no question is worse than its absence.

### `0018_timestamptz`

Every instant column becomes `timestamptz`. The calendar-day columns (`transaction_date`,
`movement_date`, `effective_date`) are deliberately left as `date` — see below.

The reason is that each of these columns has two writers, and on a naive column they agree only
by accident:

  * the application writes through Drizzle, which serialises a JS Date with `toISOString()`.
    A `timestamp without time zone` column parses that, discards the `Z`, and keeps the UTC
    wall clock — regardless of any session setting.
  * `DEFAULT now()` produces a `timestamptz`, and the implicit cast into a naive column
    converts it to the *session's* TimeZone wall clock first.

With the session on UTC — the default for both the postgres:17 image and Cloud SQL — those two
land on the same value, which is why nothing has been visibly wrong. But it holds by
configuration rather than by design: set `timezone` on the instance, or let a client connect
with its own, and the same column starts accumulating both conventions with nothing on the row
to say which one produced it. At that point the two are no longer separable, because the
offset needed to tell them apart is precisely what a naive column threw away.

`timestamptz` stores an absolute instant, so both writers agree by construction and the session
setting stops mattering. It also means psql, the Cloud SQL console and any BI tool render these
in the reader's timezone with an offset attached, instead of a bare UTC wall clock that reads
seven hours off to anyone in Bangkok with nothing marking it as UTC.

`USING ... AT TIME ZONE 'UTC'` is exact here, and only here: it asserts the existing naive
values are UTC wall clocks, which is true because every row to date was written under a UTC
session by both paths above. Run this before that assumption stops holding. Note that a bare
`ALTER ... TYPE timestamptz` would *not* be equivalent — it interprets existing values in the
session timezone, so it is correct only when that session happens to be UTC. The explicit
`AT TIME ZONE 'UTC'` makes the migration produce the same result whoever runs it.

The application is unaffected: Drizzle's contract is a JS `Date` in and a JS `Date` out for
both column types. Only `mapFromDriverValue` changes, and only by no longer having to append
`+0000` by hand to a value that now carries its own offset.

Not converted, on purpose: `whole_buy_transactions.transaction_date`,
`whole_sell_transactions.transaction_date`, `retail_buy_transactions.transaction_date`,
`retail_sell_transactions.transaction_date`, `inventory_movements.movement_date`,
`stock_gain_adjustments.transaction_date`, `stock_loss_adjustments.transaction_date` and
`unit_conversion.effective_date` (the only time column on that table). Those are business days,
not instants — all a picked day
decides is which Fri–Thu settlement period a record falls in, and that boundary is a day
boundary. Giving them a timezone would reintroduce the ambiguity the business-date design
exists to remove.
Added by 0017, so the only two that were ever naive for less than one release.
